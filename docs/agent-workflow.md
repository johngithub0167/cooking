# Agent 协作工作流程

> 面向：项目负责人（你）。说明配置好 CodeBuddy 之后，**怎么让这几个 Agent 真正协同干完这个项目**。
> 配套文件：`docs/codebuddy-guide.md`（怎么下达指令）、`00-management/task-board.md`（任务清单）
> 最后更新：2026-09-24

---

## 0. 先选工作模式（重要）

两种模式都对，按阶段选：

| 模式 | 怎么做 | 什么时候用 |
| --- | --- | --- |
| **模式 1：一个对话切角色** | 同一会话里用 Agent 选择框切换角色，**换角色前 `/clear` 清空历史** | **推荐先用这个**：项目初期、熟悉流程阶段 |
| **模式 2：多对话并行** | 每个会话固定一个角色，同时推进 | 熟悉之后、想省时间时 |

两种模式的差别只在「上下文是否共享」和「能否并行」，**任务流程、交接规则、验收关卡完全一样**。

**模式 1 的 `/clear` 很关键**：不清空的话，后端代码和前端代码会堆在同一个上下文里，模型容易把后端的字段名套到前端，或者改前端时顺手改后端。

> 下文第 1~2 节讲的是模式 2（并行）的规则；如果你用模式 1，可以直接跳到第 3 节，只需要记住「换角色前 `/clear`」。

## 1. 三种会话，别混在一起

| 会话类型 | 用途 | 用哪个角色 |
| --- | --- | --- |
| **执行会话** | 写代码、跑命令、改配置 | backend-developer / frontend-developer / devops |
| **检查会话** | 验收、写用例、跑测试、查缺陷 | tester |
| **协调会话** | 汇总进度、解决冲突、更新看板 | 不用角色，或你自己手动改 |

**规则：一个执行会话只干一个工程。** 后端会话只碰 `04-backend/`，前端会话只碰 `03-frontend/`，运维只碰 `06-devops/`、`07-delivery/` 和根目录配置。

## 2. 并行还是串行

### 可以同时跑（目录不冲突）

```text
会话 A：backend-developer   →  04-backend/server
会话 B：frontend-developer  →  03-frontend/mobile
会话 C：devops              →  根目录 + 06-devops
```

### 不能同时跑

- 同一工程开两个会话（会互相覆盖文件）；
- 两个会话同时改 `00-management/task-board.md`（整文件覆盖，必丢数据）。

### 看板更新的安全做法

并行阶段**不要让 Agent 直接改 `task-board.md`**。改成：

- 每个角色维护自己的状态文件：`00-management/status/backend-status.md`、`frontend-status.md`；
- 阶段结束后，由你在**协调会话**里一次性合并到 `task-board.md` 和 `progress.md`。

如果只有一个会话在跑，可以直接让它改看板。

## 3. 单个任务的标准闭环（7 步）

每个任务都按这个流程走，不要跳步：

```text
① 领任务  → 你给出任务编号（如 BE-011）与边界
② 读文档  → Agent 读 CODEBUDDY.md + 角色必读文件
③ 复述计划 → Agent 说明理解与执行步骤，等你确认   ← 别省
④ 实现    → 只改自己目录内的文件
⑤ 自检    → 后端：跑命令自测；前端：对照 AC 编号逐条说明
⑥ 交付说明 → 按固定格式输出（见下）
⑦ 更新状态 → 写自己的 status 文件 / 更新看板
```

### 交付说明格式（每个任务结束必须输出）

```text
任务编号：
完成内容：
修改/新增文件：
验证方式（命令或访问路径）：
验证结果：
未解决问题 / 待确认：
建议下一步：
```

**"未解决问题"这一栏最重要** —— Agent 卡住时会倾向于硬编一个方案糊过去，你必须要求它把不确定的地方明确列出来。

## 3.1 实际对话长什么样（照着念就行）

```text
你：任务：BE-001 到 BE-003 ……（完整指令，末尾写"先复述你的执行计划，等我确认再动手"）

Agent：我读了 4 个文档，计划如下：
      1. 在 04-backend/server 初始化工程……
      2. 建 7 张表的 migration……
      计划这样可以开始吗？

你：（扫一眼，检查 4 件事，见下）
    → 没问题：「确认，开工。每完成一个任务停下来汇报。」
    → 有问题：「第 2 条不要做 XXX，只做 YYY，改完再复述一遍。」

Agent：BE-001 完成。修改/新增文件：……验证方式：npm run dev + curl /api/health

你：自己跑一遍验证了 → 通过 → 「继续 BE-002。」
   （跑不通就把报错贴回去：「启动报错，日志如下：……」）

Agent：BE-002 完成……
你：全部通过 → 「可以，提交一次 Git。」→ 确认没问题 → 准备换角色
```

### 复述之后，你要检查哪 4 件事（10 秒）

1. **它列了读了哪些文件吗** —— 没列，说明它没真读，让它先读；
2. **它要改的文件路径在它自己目录里吗** —— 出现别的模块路径，立刻叫停；
3. **有没有"顺便把 XX 也做了"** —— 不在本次任务范围内的，砍掉；
4. **它有没有提出疑问或标「待确认」** —— 没问题反而要警惕，可能是自己瞎假设了。

### clear 的正确时机

| 情况 | 要不要 /clear |
| --- | --- |
| 同一角色，接着做下一批任务（BE-001~003 → BE-016） | **不要**，上下文有用，它能记住刚才的结构 |
| 换角色（backend → frontend） | **要** |
| 换阶段（开发 → 测试） | **要** |
| 上下文太长、开始胡说 | **要** |

**顺序：验证通过 → 让它提交 Git → 再 /clear → 切下一个角色。**

## 4. 四条交接链

### 4.1 后端 → 前端（最关键）

```text
后端按 api-design.md 实现接口
   ↓
后端自测通过（curl / 健康检查通过）
   ↓
后端在交付说明里写明：已完成的接口清单 + 本地访问地址
   ↓
前端按同一份 api-design.md 联调
```

**接口还没好时前端怎么办：**

1. 先做不依赖接口的页面骨架、路由、组件、状态管理；
2. 遇到缺接口，**明确标注阻塞**（缺哪个接口），继续做别的部分；
3. **禁止用假数据 mock 掉真实接口然后声称已完成** —— 这条已写进前端规则。

### 4.2 前端 → 后端（发现问题）

前端发现接口字段与文档不一致时：

```text
不要自己改字段名去适配 → 在交付说明里记录 → 交给后端会话修正实现
```

**铁律：文档是唯一依据。实现与文档不一致，改实现，不改文档**（除非评审后确认改文档）。

### 4.3 开发 → 测试

一个阶段的代码完成后，开 `tester` 会话：

```text
tester 读 acceptance-criteria.md
   ↓
把 AC 条款转成测试用例（05-testing/test-cases.md）
   ↓
接口测试 + 功能测试
   ↓
输出 test-report.md + 缺陷清单 bugs.md
```

### 4.4 测试 → 开发（返工）

缺陷单格式：

```text
缺陷编号：BUG-001
关联 AC：
问题描述：
复现步骤：
预期结果：
实际结果：
严重程度：高 / 中 / 低
日志或截图：
建议处理方向：
```

把缺陷单贴回对应角色的会话里修，修完让 tester 复测。

## 5. 变更与冲突处理

| 情况 | 处理方式 |
| --- | --- |
| 需要改接口字段 | 先改 `02-design/api-design.md` → 记 `decisions.md` → 再改代码 → 通知前端 |
| 需要改技术选型 | **不允许 Agent 自行决定**，必须先问你 |
| 发现其他模块的 bug | 只记录到自己的 status 文件，不越权修改 |
| 需求里没说清楚 | 标记「待确认」，写进 `open-questions.md`，不得自行假设 |
| 两个会话改了同一个文件 | 停止并行，串行处理，人工确认保留哪一份 |

## 6. 验收关卡：你什么时候介入

每个关卡你只需要看固定的东西，不必全程盯着。

| 关卡 | 时机 | 你看什么 | 放行标准 |
| --- | --- | --- | --- |
| **Gate 1** | 工程初始化后 | `04-backend/server` 目录结构、`GET /api/health` 能通、前端能启动 | 三条命令都能跑起来 |
| **Gate 2** | 后端接口完成 | `02-design/api-design.md` 里 15 个接口逐个 curl 通 | 全部接口返回 `code: 0` |
| **Gate 3** | C 端完成 | 手机上实际操作一遍：推荐 → 总菜单加入/删除 → 提交 → 历史 | 主链路走得通，无报错 |
| **Gate 4** | 后台完成 | 后台实际操作：登录 → 加分类 → 加菜品（含传图）→ 看记录 | C 端能立刻看到新加的菜 |
| **Gate 5** | 测试后 | `05-testing/test-report.md` | 高严重度缺陷清零 |

**每个 Gate 通过后，让它提交一次 Git**，这样随时能回滚。

## 7. cooking 项目第一批实操

### 第一轮

模式 1：一个对话，先选 `devops` 干完 → `/clear` → 切 `backend-developer`。
模式 2：开一个 `devops` 会话 + 一个 `backend-developer` 会话。

任务内容：

```text
OPS-001  Git 初始化 + .gitignore
OPS-002  完善 .env.example
OPS-003  一键启动脚本
BE-001   Express 工程骨架（配置/数据库连接/统一响应/错误处理/日志/健康检查）
BE-002   数据库连接 + 执行 migration 建表
BE-016   种子数据（约 30 道家常菜）
```

后端指令（复制即可）：

```text
用 backend-developer 角色，完成 BE-001、BE-002。

先读：PROJECT_RULES.md、02-design/technical-architecture.md、
02-design/database-design.md、02-design/api-design.md、.codebuddy/rules/backend-rules.md。

要求：
1. 在 04-backend/server 下按文档第 3 节目录结构初始化 Express 4 + Sequelize 6 + mysql2 工程；
2. 实现配置读取、数据库连接、统一响应、统一错误处理、请求日志；
3. 新建全部 migration 并建表（7 张表）；
4. 加一个 GET /api/health 返回 { code: 0, data: { status: 'ok' } }；
5. 本次不写业务接口。

先复述计划，等我确认再动手。完成后把结果写进 00-management/status/backend-status.md。
```

### 第二轮（并行）

- 会话 A：`backend-developer` → BE-010 ~ BE-015（分类、菜品、上传、推荐、菜单接口）
- 会话 B：`frontend-developer` → FE-001 ~ FE-003（C 端工程骨架、请求封装、今日菜单状态），**等接口就绪后再做 FE-010 之后的业务页面**

### 第三轮

- 会话 C：`frontend-developer` → AD-010 ~ AD-016（后台页面）
- 会话 D：`tester` → TEST-001 ~ TEST-006

### 第四轮

- `devops` → OPS-010 ~ OPS-013（部署、备份、发布检查）
- 你做 DELIVERY-001 验收

## 8. 每次开工的固定开场白

不管哪个角色、哪种模式，第一句都套这个模板：

```text
（模式 1 先在对话框执行 /clear，再选角色）

用 [角色名] 完成 [任务编号]。

必读：[列出文档路径]

要求：
1. [具体要求]
2. 只改 [目录]，不要动其他模块；
3. 不确定的地方标「待确认」，不要自行假设；
4. 完成后按交付格式输出。

先复述你的理解和执行计划，等我确认再动手。
```

## 9. 常见坑

| 坑 | 表现 | 避免方式 |
| --- | --- | --- |
| Agent 不看文档就开写 | 字段名和接口文档对不上 | 强制"先复述再动手"，且要求它列出读了哪些文件 |
| 用 mock 假完成 | 前端看起来能跑，一联调就崩 | 规则里明令禁止，验收时抓一个真实接口验证 |
| 顺手改别的模块 | 后端改了前端代码 | 指令里写死目录边界 |
| 两个会话互相覆盖 | 文件莫名回退 | 不同工程才并行；共享文档串行改 |
| 进度丢失 | 换会话后不知道做到哪了 | 每轮结束更新 status 文件与 progress.md |
| 技术选型被偷偷换掉 | 装了文档里没有的依赖 | Gate 检查时看一眼 package.json |
